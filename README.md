# unisono

unisono streams uncompressed audio over IP to multiple receivers and synchronizes playback. It uses stochastic optimal control to deliver best possible mix of synchronization, low latency and reliability over a variety of links (wired or WiFi). It is designed for small processing quanta and supports realtime scheduling.

**Status: early development. Nothing here can be used yet.**

Unisono is written in Rust and formally verified. The properties of its core are proved in Lean 4: the
core is translated to Lean by [Aeneas](https://github.com/AeneasVerif/aeneas),
and the theorems are statements about that translation.

## What works

Built and tested on Linux, without audio hardware:

- A sender and receivers as processes (`unisono send`, `unisono receive`),
  over UDP, with a software device that captures a test signal and one that
  plays to nothing at a rate of its own, or with PipeWire when the program is
  built with the feature `pipewire`. Receivers on clocks of their own, behind
  links with delay, jitter and loss, play each frame within tens of
  microseconds of the same instant.
- The receivers measure what each stretch of the stream needed to be played
  in time and report it; the sender chooses the latency that all receivers
  hold from those reports and moves it along a line that every receiver
  follows at once.
- A receiver asks for the frames of packets that were lost, and the sender
  sends them again; in simulation this costs less than any copy or code sent
  in advance, and adds only what was lost. Frames that still do not arrive
  in time are concealed.
- Counters and gauges in the Prometheus text format (`--metrics`), among them
  counts that hold each assumption of the model against what happens.

Not built yet: a backend for ALSA, an interface for C, platforms other than
Linux, and any measurement on audio hardware.

`docs/model.md` states the problem and what is assumed, `docs/theorems.md`
lists what is proved, and `docs/protocol.md` gives the packets.

## Layout

| Path | Content |
|---|---|
| `crates/unisono-core` | The pure core: no input or output, no allocation, nothing that can panic |
| `crates/unisono-dsp` | Signal processing: the resampler that corrects clock drift, sample formats, fades and the concealment of gaps |
| `crates/unisono-metrics` | Counters, gauges and histograms that real-time threads update without waiting, and their export in the Prometheus text format |
| `crates/unisono-runtime` | The threads of a sender and of a receiver around the core: sockets, clocks, the rings between threads, the choice of the level |
| `crates/unisono-pipewire` | Capture and playback through PipeWire |
| `crates/unisono` | The program |
| `crates/unisono-sim` | A deterministic simulation of clocks and links, for tests without hardware |
| `crates/translation-check` | Prints inputs and results of the core's functions, to compare the Lean translation with |
| `crates/reachable`, `crates/cycle-cost` | The inspection of the machine code of the real-time threads, and the count of what a cycle costs |
| `lean/UnisonoCore` | The Lean translation of the core, generated by `just translate` |
| `lean/Unisono` | Specifications and proofs; `lean/Unisono/Model` holds the theorems about the problem itself |
| `lean/TranslationCheck.lean` | Evaluates the translation on the printed inputs and compares the results |
| `containers` | A container with PipeWire for the tests against a real audio system |
| `docs` | The model, the theorems, the protocol, the concealment of gaps, the real-time path, and which Rust the core may use |
| `tools` | Scripts that fetch and run the translator, the container and the inspection |

## Checking

`just check` runs what continuous integration runs:

1. formatting, lints and tests of the Rust;
2. compilation for every target platform;
3. an inspection of the machine code of the functions that run on real-time
   threads: it must not enter the kernel, call an allocator, or be able to
   panic;
4. a fresh translation of the core, which must equal the one in `lean/UnisonoCore`;
5. the proofs;
6. the comparison of the translation with the Rust on the same inputs.

It needs [rustup](https://rustup.rs), [just](https://just.systems),
[elan](https://github.com/leanprover/elan) and, for step 4,
[opam](https://opam.ocaml.org). The first run builds Aeneas and its Lean
library, which takes a while; later runs take about a minute.

After a change to the Rust of the core, `just translate` writes the translation
again.

## How the proofs relate to the Rust

A theorem in `lean/Unisono` is about a function in `lean/UnisonoCore`. It
says something about the Rust to the extent that the translation is faithful,
and three things support that:

- the translation is regenerated and compared on every check, so it cannot go
  stale;
- a function of the standard library without a Lean model fails the
  translation, so none enters the proofs as an axiom, and
  `lean/Unisono/Audit.lean` pins the axioms each theorem uses;
- every translated function is evaluated in Lean on the inputs the Rust was run
  on, and the results must agree.
